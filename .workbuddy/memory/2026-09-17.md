## 新增「分享任务结果到微信/钉钉」功能（D:\workagent，已完成）

用户需求：把指定任务的结果分享到微信或钉钉。开工前用 AskUserQuestion 定了三个边界：

- 投递方式：**剪贴板 + 唤起客户端**（用户明确选此，未做 Webhook 直发）。
- 入口：**右侧工作区顶栏**（不是消息悬停栏、不是左侧任务列表）。
- 内容：**仅回答正文**（不含任务标题、提问、产出文件清单、来源、工具步骤）。

### 关键设计决定（后续改动请沿用）

- **组稿在渲染进程，投递在主进程**。`App.tsx` 的 `snapshot.messages` 是全量 transcript（`getThreadSnapshot` 无 cursor 时用 `listRecentMessages(threadId, messageCount)`），所以渲染进程手上就有完整消息；组稿放渲染进程才能保证「分享的内容 == 用户看到的内容」。主进程只做剪贴板 + 检测 + 唤起。
- **微信个人版 / 钉钉个人版都没有开放的消息发送 API**，因此是「复制到剪贴板 + 唤起客户端 + 用户手动粘贴」，不自动发送。这是产品事实，不是偷懒。
- 平台格式差异：钉钉保留 Markdown，微信走 `stripMarkdown()` 转纯文本（标题/加粗/行内代码/链接/列表/代码块/表格分隔行都要处理，否则微信里显示一堆 `**`）。
- 回答正文提取复用 `parseStructuredEventBlocks`（`renderer/lib/conversation-utils.ts`），只保留 `commentary` / `final` 块，丢掉 tool_call / tool_result / file_* / test_result，避免把工具调用 XML 粘进分享内容。

## 分享功能 v2：改为「对话长图 + WorkBuddy 式渠道宫格」（已完成，待运行验证）

用户新需求：分享面板的 UI 交互参考 WorkBuddy，且分享出去的内容不能是纯文本，要带格式、跟聊天内容一样。

### 先做的事：把 WorkBuddy 自己的分享实现挖出来当参考

本机装了 WorkBuddy，渲染层在 `D:\Programs\WorkBuddy\resources\app.asar`（297MB）。asar 格式可直接用 Python 解析：前 8 字节里 offset 4 起的 uint32 = 头部 JSON 长度 N，数据起始 = 8 + N，每个 entry 的 `offset`/`size` 相对数据起始。之后 `walker` 递归 `files` 即可列出全部 20474 个文件，按路径 regex 定位。

结论（值得记下来，是产品参考事实）：
- 弹窗 `shareTask.dialog`（i18n 前缀 `shareTask.*` / `shareSelection.*` / `shareTaskPreview.*`，中文串在 `renderer/assets/zh-cn-*.js`）。
- **它分享出去的不是文字、不是图片，而是公开链接**，落地页是对完整对话流的静态还原（代码高亮/表格/mermaid/产物卡片全在），带「{N} 轮对话 · {M} 次工具调用 · {K} 个文件」和 AI 免责声明。
- 实现方式（`packages/agent-ui/src/utils/share/dom-snapshot-share/*`）：渲染对话流到隐藏容器 → `serializeDomToHtml` 序列化 DOM → `collectPageStyles` 内联全部 CSS → `snapshotCssVariables` 快照主题变量计算值 → 图标字体转 base64 内联 → 上传。**这就是「带格式分享」的标准解法**。
- 渠道宫格：微信/朋友圈/复制链接/生成二维码/浏览器打开/X/Facebook/Telegram/Discord/Slack；唤起微信失败走小程序码兜底；另有「下载 MD」。

### 本次的边界（AskUserQuestion 已确认）

- 产物形态：**长图 PNG**（用户选；公开链接需要后端，codexh 是纯本地应用，不做）。
- 弹窗：**重做成 WorkBuddy 式渠道宫格**。
- 因为分享的是图片而非链接，二维码/浏览器打开渠道无意义，改为「复制图片 / 保存图片 / 复制 Markdown」。

### 长图管线设计（`renderer/lib/share-capture.ts`，零新增依赖）

`captureElementToPng` 走 WorkBuddy 同源思路，但对外部资源做了处理：
1. 离屏 host（`position:fixed;left:-200000px`）内 `createRoot` 挂载分享卡片 → 等 `document.fonts.ready` → **轮询高度直到稳定**（mermaid/echarts 是异步渲染，不要用固定 delay）→ 最多 14 轮 ×160ms。
2. `cloneNode(true)` 后内联资源：`<canvas>`→`toDataURL` 转 `<img>`（echarts 是 canvas，必须转，否则截图里图表是空的）；`<img src>` 用 `fetch` 转 dataURL（`codexh-media://` 协议注册时带了 `supportFetchAPI:true`，所以 fetch 可用）。
3. **用 `XMLSerializer` 而不是 `outerHTML`** 序列化克隆体——`outerHTML` 会产出 `<br>` 这类非自闭标签，塞进 SVG 的 XML 解析会直接整份失败、得到空白图。这是这个技术路线最容易踩的坑。
4. CSS 从 `document.styleSheets` 的 `cssRules.cssText` 运行时收集（**renderer 生产环境也是 `loadURL` 本地 http server 起的，不是 file://，所以同源可读**，无需 `?inline` 打包，也不用担心 file:// 下 CSSOM 抛 SecurityError）。主题变量用 `getComputedStyle(document.body)` 快照成内联声明写在 holder 上。
5. 分片栅格化：SVG 的 `width/height` 用 `width*scale`，`viewBox="0 sliceTop width sliceHeight"`，`<rect>` 铺满整高做底色。一片一片 `drawImage` 到同一 canvas。
6. 兜底：`looksBlank()` 把画布缩到 32×32 算亮度极差，< 6 判定为空白图 → 抛错，而不是静默分享一张白图。超高（>16000 CSS px）抛 `ShareCaptureTooLargeError`，UI 提示缩小范围（对齐 WorkBuddy「文件超过 20MB 无法分享」的诚实做法）。

### 其它关键点

- 轮次/范围模型换成「按 user 消息切轮」(`lib/share-turns.ts`)，而不是运行时的 `turnRunId`（乐观消息与历史消息没有 turnRunId）。**分享内容现在包含用户提问**，这才是「和聊天内容一样」。
- 工具调用/文件数按轮次聚合的 `turnRunIds` 归因，`computeShareStats` 输出 WorkBuddy 那种统计条。
- 纯逻辑全部放 `share-turns.ts`（DOM-free，可在 vitest node 环境测）；截图像素相关才放 `share-capture.ts`。
- 旧的纯文本链路（`share-text.ts` / `share:send` / `shareTaskResult`）**保留不删**，`copyMarkdown` 渠道仍可退化为文本；`stripMarkdown` 补了 hr 行剔除（`---` 在纯文本里是噪音）。

### 验证

- `vitest run tests/share-turns.test.ts tests/share-task-result.test.ts` → 25 passed（新增 12 个）。
- `tsc --noEmit`：新增文件零报错；仅剩两条历史报错在 `App.tsx(1957)`（`typed.payload`，旧行号 1946，与分享无关）。

## 诊断：子智能体跑完却显示「排队中」（已定位，未改码）

用户截图：右侧子智能体面板显示「羲和 · security-reviewer · 等待可用执行槽位」，状态「排队中」，阶段进度只有「排队准备」；主对话里也有「羲和|排队中」状态条。

### 结论：子智能体**有用**，是状态映射错了

用真实数据验证（`~/.codexh/codexh.sqlite` + `~/.codexh/logs/runtime.jsonl`）：

- 该线程 `6dcbd30a-a943-42f3-b6be-36a4b07a6ebd`（`/root/security-reviewer`）：`turn_runs.status = completed`，189,663 prompt / 4,205 completion tokens，跑了 65 秒，最终 assistant 消息落库（RiskEmpRequestValidator / OpenService 的 SQL 注入面结论）。
- 主线程 `wait_agent` 拿到的返回是 `{"agents":[{"status":"queued","summary":"### C. status / emp_state / ..."}]}` —— **summary 内容是完整的真实产出，只有 `status` 字段被写成了 queued**。也就是说结果交付没问题，是状态标注误导主模型（会让它以为子任务还在排队）。
- 但 `threads.status = idle`（`updated_at` 比 turn 完成时间晚 12ms）。

### 根因链（三处叠加）

1. `packages/agent-runtime/src/index.ts` 约 5658 行，成功收尾时：`status = terminalDisposition === "awaiting_user_confirmation" || providerOutputLimitEncountered ? "idle" : "completed"`。`providerOutputLimitEncountered` 是**整轮粘性标记**（约 3542 行置 true，恢复重试后不复位）。runtime.jsonl 里有 `02:49:39 provider.output_limit attempt=1 "response reached its output limit"`，之后重试成功、turn 正常 completed，但线程被写成 `idle`。子智能体不可能命中 `awaiting_user_confirmation`（`resolveTerminalTurnDisposition` 对 child 强制 `gpaStage: "off"`，且该线程 gpa_state_json 只有 `{"fullAccess":true}`）。
2. `apps/desktop/src/main/app.ts` 约 4557 行 `buildSubagentEnvelope`：`thread.status === "idle" → "queued"`。这个映射只在「创建了但从未派发」时才成立（`spawnAgent` 里 `status: queued ? "idle" : "running"`），却被当成了 idle 的通用语义。
3. `apps/desktop/src/renderer/cards/runtime-cards.tsx` 约 288 行 `resolveSubagentDisplayState`：`if (queued || result?.status === "queued") return "queued"` 排在 completed/failed/interrupted **之前**，于是排队把终态全遮掉；`getSubagentPhases` 更是在 queued 时直接短路返回「排队准备」。

### 第一步（最关键）：全量日志指纹扫描，别先读代码

写脚本扫 `~/.codexh/logs/sessions/*.jsonl`：按 `turnRunId` 聚合 `runtime.event` 里的 `message.created(assistant, len)` 与 `assistant.completed(messageId, discarded)`，找出「最后一条 len>150 的 assistant 消息，其 id 从未出现在任何 `assistant.completed.messageId` 里」的轮次。60 个会话扫出 **28 个**命中，其中 24 个都伴随 `turn.failed`。→ 说明「结论没渲染」不是随机 UI 抖动，而是有一类可枚举的轮次形态。

### 结论：主因在渲染层 CSS，不在事件链（DOM 里有、肉眼没有）

- `timeline.css`：`.task-timeline .message-card { animation: timeline-enter 180ms ease-out both; }`，而 `@keyframes timeline-enter { from { opacity: 0 } }`；另有 `.message-card.assistant.is-finalizing-from-draft { animation: assistant-finalize-enter 240ms ... both }`（from opacity .28）。
- `styles.css`：`.chat-transcript > * { content-visibility: auto; contain-intrinsic-size: auto 180px; }`（注释写着「skip offscreen layout and paint」）+ `.chat-scroll { contain: layout paint }`。
- 组合起来：新追加的结论卡片在插入/重排瞬间若被判为屏外，Chromium 会**跳过**其渲染，入场动画登记了但时钟不推进；`fill-mode: both` 把它钉在 `from` 帧 → **留在 DOM 里但 opacity 0**。`content-visibility` 的 skipped→relevant 转换不会重跑动画，所以滚动到它也不会恢复。
- `App.tsx:7026` 的 transcript 容器带 `key={activeSnapshotThreadId}` → **切会话 = 整棵 transcript 重挂载** → 动画重播 → 结论出现。这正是「切聊天就回来」的原因。

修法（按风险从低到高）：① 去掉这几个入场动画的 `both`（动画没跑就是自然 opacity 1，彻底消除这类「卡在首帧」）；② 仿照已有的 `.chat-transcript > .message-card.user { content-visibility: visible }`，给最终/正在淡入的 assistant 卡片也加 `content-visibility: visible`；③ reduced-motion 分支补上基础入场动画（现在只关掉了 `is-finalizing-from-draft`/`is-sending`，基础 `timeline-enter` 仍带 `both`）。

### 顺带查实的三处事件链缺陷（非本次主因，但同源）

1. provider 失败轮次的事件顺序是「先删草稿、后写结论」：`packages/agent-runtime/src/index.ts` catch 块（~7352 `if (activeDraftId) emit assistant.completed{discarded:true}`）跑在失败说明消息 `buildRuntimeFailureRecoveryMessage`（~1852）落库之前；而 `renderer/core/thread-ui-state.ts` 的 `shouldForceFullSnapshotForRuntimeCompletion` 对 `discarded:true` 返回 **false** → 「草稿已删 + 不强制全量重取」没有保底重同步（带 messageId 的正常收尾会强制重取，所以只有这类轮次会丢）。
2. `apps/desktop/src/main/app.ts getThreadSnapshot`：先跑查询、**后**取 `observedAt`（1023-1044），落在「查询之后、取游标之前」的消息会被本次增量漏掉，且 `listMessagesCreatedSince` 用 `created_at >= observedAt`（storage.ts:1692）让后续增量也跳过它 —— 增量游标存在时间窗空洞。正确做法是游标在查询前取，或用 (created_at, rowid) 水位。
3. `thread-ui-state.ts prunePersistedRuntimeMessageMap` 的兜底缓存只留最近 64 条，长回合（几十条 tool 消息）会削掉兜底能力。

### 可复用的验证习惯

- 判断「渲染没出来」优先做**二分**：先在 Elements 里搜结论文本 —— 搜得到但看不到 = 纯渲染/样式问题（本次）；搜不到 = 数据/事件问题，再去查 snapshot 与事件链。
- 本仓库 dist 由 `electron-vite build` 生成，`dist/main/index.js` mtime 晚于所有源码 mtime 才能确认「跑的就是这份 src」；否则可能在看旧代码。

## 修 v2：结论不渲染的**真主因**（上一轮 CSS 判断是错的）—— 自动滚动释放 + 虚拟化（已落地，构建已核验）

用户反馈上一轮改完「还是要切一下重新加载才出来」。这轮追到真根因，**与 CSS 无关**。

### 判据链（真实现场：1676 条消息 / 62 轮的长会话）

1. **数据/事件层全对**：结论 `aecea7fc`（1499 字、`metadata_json` 为 null）已落库；`message.created` 的 `threadId` / `payload.message.threadId` 都正常；`assistant.completed` 带 `messageId`；97ms 后 `thread.updated{completed}` → 不是丢事件/丢数据。
2. **`VirtualizedTimeline` 的阈值是 80 个条目** —— 长会话必然启用虚拟化，条目不在 `range` 内就**根本不挂载**（滚都滚不到）。
3. `settleAutoScroll()`（`App.tsx` ~3914）在收尾后 **320ms 把 `shouldAutoScrollRef` 置 false**。
4. 结论卡片高度在 320ms 之后仍在长：异步 markdown 高亮 / `![图](C:/…)` 本地图片解码 / 字体换挡；而 `.chat-scroll` 是 **`overflow-anchor: none`** → 不补偿滚动位置。
5. 既有的 ResizeObserver 补偿（`App.tsx` ~4136）判的是 `shouldAutoScrollRef.current` → 释放后**失明** → 渲染窗口不再跟到队尾。
6. 切会话走 `openThread(id, { scrollToLatest: true })`（~6703）→ **强制贴底** → 这就是「切一下才出来」的真实机制（不是我上轮以为的「重挂载重播动画」）。

### 改动

- `App.tsx`：新增 `isTranscriptAtLatestRef`（与 `isTranscriptAtLatest` 同步，用 useEffect），把既有 ResizeObserver 的判断放宽为
  `if (manualTranscriptScrollRef.current) return; if (!shouldAutoScrollRef.current && !isTranscriptAtLatestRef.current) return;`
  （state 只在 scroll 事件里更新，内容增长不触发 scroll，所以释放后它仍是 true —— 这就是兜底能成立的原因。）
- `timeline/virtualized-timeline.tsx`：新增导出 `resolveVirtualizedRenderRange()`，`followLatest` 时保持窗口大小、强制 `end = itemCount`，把渲染窗口钉到队尾。
- `styles.css`：补掉上一轮漏掉的 `.chat-scroll .chat-transcript.motion-thread-content { animation: thread-transcript-enter … }` 的 `both`（from `opacity: 0`，作用在整个对话容器上）。
- 测试：`tests/virtualized-timeline.test.ts` +3 例（tail pinning）；`tests/transcript-entry-motion.test.ts` 把 `thread-transcript-enter` 纳入断言 + 新增 observer 守卫。

### 验证

- 全量 `vitest run` → **69 files / 1216 passed**（`git-service.test.ts` 这次也过了）。`tsc --noEmit` 全是既有历史报错，改动文件零新增。

### 教训

- **上轮教训的加强版**：凭静态 CSS 推断（`content-visibility` + animation `both`）看似自洽，但**没先确认会话是否触发虚拟化**就定了主因 → 用户一复现就打回。以后这类症状**第一步查会话条目数 / 虚拟化阈值**。

- **长会话（>80 条）+ 尾部含异步资源（图片 / mermaid / hljs）** 是本 bug 的触发组合，也解释了「偶发」。

1. **主进程→渲染进程逐 delta 直通，节流形同虚设**。`packages/agent-runtime/src/index.ts` 的 `onTextDelta` 传了 `immediate: true`，而 `shouldPublishAssistantDraftUpdate(last, now, force)` 里 `immediate` 会把 `force` 变 true → 绕过 `ASSISTANT_DRAFT_UPDATE_MIN_INTERVAL_MS = 100` 那个门限。结果**屏幕节奏 == 网络分包节奏**，这就是「一个字 / 几个字交替」的机制。
2. **reasoning（思考过程）连节流都没有**：`updateDraftReasoning` 每个 delta 直接 emit 一次。思考流是最长的，所以字越多越卡。
3. **渲染侧 `chunks: [...prev, delta]` 是 O(n²)**：`renderer/lib/conversation-utils.ts` 的 `reconcileAssistantDraftStreamUpdate` 每次 delta 复制整个数组，`transcript.tsx` 再 `chunks.map()` 成 N 个 `<span>` 交给 React 逐一 diff。长回复越到后面越顿，就是这个（`reasoningChunks` 同理，且它在 `<details>` 里还每帧 `scrollTop = scrollHeight` 强制布局）。

排除项（查过，不是原因）：`addRuntimeEvent` 对 draft 事件早返回（`storage.ts:3531` 只落 context_compacted/measured）；`compactRuntimeToolResult` / `sanitizeRuntimeEventForLog` 对 draft 事件都是 O(1) 早返回。

### ⚠️ 推翻上一节的一条结论（重要）

上一节写：「**git 自己从不把文件删进回收站**（gc/prune/stash 都是直接 unlink）。所以这是外部工具/资源管理器式删除」。
**这条在本机不成立。** 本次做了对照实验：

| 删除方式 | 是否进回收站 |
|---|---|
| Python `os.remove`（= Win32 `DeleteFileW`，与 git 的 unlink 同源） | **是**（2026-09-17 16:53:28） |
| PowerShell `Remove-Item` | 否 |
| cmd `del` | 否 |

### 本次恢复路径（与上次不同，更优）

1. 解析回收站 `$I` 拿原始路径。**关键坑**：`pathLength` 在 v1（字节）/v2（字符）语义不同，别用它 —— 直接 `raw[28:].decode("utf-16-le", "replace").split("\x00")[0]`。

3. 恢复规则：**可变量（`refs`/`logs`）只取最后一批**（否则会把旧 sha 覆盖回去，比损坏更难查）；**对象文件内容寻址，全批次恢复都幂等**；排除 `index`/`index.lock`/`index.stash.*`/`packed-refs.lock`/`HEAD`/`config`/`hooks`/`info`/`commit-graph`。

### 教训

### 第二件事：排序键（storage.ts 三处，必须一起改）

只改 `ORDER BY` 是**不够的** —— 还有一处会把马太效应从 usage 转移到 updated_at：

1. **`searchSelfImprovementMemories` 命中路径**（~2968）：`ORDER BY score ASC, m.updated_at DESC`（原 `score ASC, m.usage_count DESC, m.updated_at DESC`）
2. **同函数 fallback**（~2976）：`ORDER BY updated_at DESC`（原 `usage_count DESC, updated_at DESC`）
3. **⚠️ `markSelfImprovementMemoryUsed`**（~2989）：`SET usage_count = usage_count + 1, last_used_at = ?` —— **删掉了 `updated_at = ?`**。原因：recall 会刷 updated_at，而 updated_at 同时是**召回 tie-break 键**和 **retention 判据**（`pruneSelfImprovementMemories` 的 `updated_at < before`）→ 被召回过一次的记忆会永远"最新"且**永不过期**。改后语义分离：`updated_at` = 内容最后变更，`last_used_at` = 最后召回。

**有意保留未动**：`pruneSelfImprovementMemories` 里那两处 `ORDER BY usage_count DESC`（~3012/3017）—— 淘汰时按使用频率保留高频是合理的，与召回无关。`error_solutions` 表的 recall 刷 updated_at 也**未动**（它的列表语义本就是"最近使用优先"，且有独立 `expiresAt`，不依赖 updated_at 判过期）。
