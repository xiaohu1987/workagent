## 新增「分享任务结果到微信/钉钉」功能（D:\workagent，已完成）

用户需求：把指定任务的结果分享到微信或钉钉。开工前用 AskUserQuestion 定了三个边界：

- 投递方式：**剪贴板 + 唤起客户端**（用户明确选此，未做 Webhook 直发）。
- 入口：**右侧工作区顶栏**（不是消息悬停栏、不是左侧任务列表）。
- 内容：**仅回答正文**（不含任务标题、提问、产出文件清单、来源、工具步骤）。

### 关键设计决定（后续改动请沿用）

- **组稿在渲染进程，投递在主进程**。`App.tsx` 的 `snapshot.messages` 是全量 transcript（`getThreadSnapshot` 无 cursor 时用 `listRecentMessages(threadId, messageCount)`），所以渲染进程手上就有完整消息；组稿放渲染进程才能保证「分享的内容 == 用户看到的内容」。主进程只做剪贴板 + 检测 + 唤起。
- **微信个人版 / 钉钉个人版都没有开放的消息发送 API**，因此是「复制到剪贴板 + 唤起客户端 + 用户手动粘贴」，不自动发送。这是产品事实，不是偷懒。
- 平台格式差异：钉钉保留 Markdown，微信走 `stripMarkdown()` 转纯文本（标题/加粗/行内代码/链接/列表/代码块/表格分隔行都要处理，否则微信里显示一堆 `**`）。
- 回答正文提取复用 `parseStructuredEventBlocks`（`renderer/lib/conversation-utils.ts`），只保留 `commentary` / `final` 块，丢掉 tool_call / tool_result / file_* / test_result，避免把工具调用 XML 粘进分享内容。

## 分享功能 v2：改为「对话长图 + WorkBuddy 式渠道宫格」（已完成，待运行验证）

用户新需求：分享面板的 UI 交互参考 WorkBuddy，且分享出去的内容不能是纯文本，要带格式、跟聊天内容一样。

### 先做的事：把 WorkBuddy 自己的分享实现挖出来当参考

本机装了 WorkBuddy，渲染层在 `D:\Programs\WorkBuddy\resources\app.asar`（297MB）。asar 格式可直接用 Python 解析：前 8 字节里 offset 4 起的 uint32 = 头部 JSON 长度 N，数据起始 = 8 + N，每个 entry 的 `offset`/`size` 相对数据起始。之后 `walker` 递归 `files` 即可列出全部 20474 个文件，按路径 regex 定位。

结论（值得记下来，是产品参考事实）：
- 弹窗 `shareTask.dialog`（i18n 前缀 `shareTask.*` / `shareSelection.*` / `shareTaskPreview.*`，中文串在 `renderer/assets/zh-cn-*.js`）。
- **它分享出去的不是文字、不是图片，而是公开链接**，落地页是对完整对话流的静态还原（代码高亮/表格/mermaid/产物卡片全在），带「{N} 轮对话 · {M} 次工具调用 · {K} 个文件」和 AI 免责声明。
- 实现方式（`packages/agent-ui/src/utils/share/dom-snapshot-share/*`）：渲染对话流到隐藏容器 → `serializeDomToHtml` 序列化 DOM → `collectPageStyles` 内联全部 CSS → `snapshotCssVariables` 快照主题变量计算值 → 图标字体转 base64 内联 → 上传。**这就是「带格式分享」的标准解法**。
- 渠道宫格：微信/朋友圈/复制链接/生成二维码/浏览器打开/X/Facebook/Telegram/Discord/Slack；唤起微信失败走小程序码兜底；另有「下载 MD」。

### 本次的边界（AskUserQuestion 已确认）

- 产物形态：**长图 PNG**（用户选；公开链接需要后端，codexh 是纯本地应用，不做）。
- 弹窗：**重做成 WorkBuddy 式渠道宫格**。
- 因为分享的是图片而非链接，二维码/浏览器打开渠道无意义，改为「复制图片 / 保存图片 / 复制 Markdown」。

### 长图管线设计（`renderer/lib/share-capture.ts`，零新增依赖）

`captureElementToPng` 走 WorkBuddy 同源思路，但对外部资源做了处理：
1. 离屏 host（`position:fixed;left:-200000px`）内 `createRoot` 挂载分享卡片 → 等 `document.fonts.ready` → **轮询高度直到稳定**（mermaid/echarts 是异步渲染，不要用固定 delay）→ 最多 14 轮 ×160ms。
2. `cloneNode(true)` 后内联资源：`<canvas>`→`toDataURL` 转 `<img>`（echarts 是 canvas，必须转，否则截图里图表是空的）；`<img src>` 用 `fetch` 转 dataURL（`codexh-media://` 协议注册时带了 `supportFetchAPI:true`，所以 fetch 可用）。
3. **用 `XMLSerializer` 而不是 `outerHTML`** 序列化克隆体——`outerHTML` 会产出 `<br>` 这类非自闭标签，塞进 SVG 的 XML 解析会直接整份失败、得到空白图。这是这个技术路线最容易踩的坑。
4. CSS 从 `document.styleSheets` 的 `cssRules.cssText` 运行时收集（**renderer 生产环境也是 `loadURL` 本地 http server 起的，不是 file://，所以同源可读**，无需 `?inline` 打包，也不用担心 file:// 下 CSSOM 抛 SecurityError）。主题变量用 `getComputedStyle(document.body)` 快照成内联声明写在 holder 上。
5. 分片栅格化：SVG 的 `width/height` 用 `width*scale`，`viewBox="0 sliceTop width sliceHeight"`，`<rect>` 铺满整高做底色。一片一片 `drawImage` 到同一 canvas。
6. 兜底：`looksBlank()` 把画布缩到 32×32 算亮度极差，< 6 判定为空白图 → 抛错，而不是静默分享一张白图。超高（>16000 CSS px）抛 `ShareCaptureTooLargeError`，UI 提示缩小范围（对齐 WorkBuddy「文件超过 20MB 无法分享」的诚实做法）。

### 其它关键点

- 轮次/范围模型换成「按 user 消息切轮」(`lib/share-turns.ts`)，而不是运行时的 `turnRunId`（乐观消息与历史消息没有 turnRunId）。**分享内容现在包含用户提问**，这才是「和聊天内容一样」。
- 工具调用/文件数按轮次聚合的 `turnRunIds` 归因，`computeShareStats` 输出 WorkBuddy 那种统计条。
- 纯逻辑全部放 `share-turns.ts`（DOM-free，可在 vitest node 环境测）；截图像素相关才放 `share-capture.ts`。
- 旧的纯文本链路（`share-text.ts` / `share:send` / `shareTaskResult`）**保留不删**，`copyMarkdown` 渠道仍可退化为文本；`stripMarkdown` 补了 hr 行剔除（`---` 在纯文本里是噪音）。

### 验证

- `vitest run tests/share-turns.test.ts tests/share-task-result.test.ts` → 25 passed（新增 12 个）。
- `tsc --noEmit`：新增文件零报错；仅剩两条历史报错在 `App.tsx(1957)`（`typed.payload`，旧行号 1946，与分享无关）。
- `electron-vite build` 全绿（renderer 3141 modules，`styles-*.css` 717.78 kB，构建产物里能搜到 37 处新类名）——CSS 语法与打包路径已验证。

- 顺手删掉了 v2 遗留的按轮选择 API（`selectableShareTurns` / `defaultShareTurnIds` / `allShareTurnIds` / `shareTurnSummaries` / `composeShareMarkdown` / `collectShareMessages` / `resolveShareTurns` + `ShareTurnSummary` 导入），避免「两套并存的选择模型」。它们的测试用例改写成了消息级的等价断言（用 `stripMarkdown` 那条 hr 断言保留）。

## 诊断：子智能体跑完却显示「排队中」（已定位，未改码）

用户截图：右侧子智能体面板显示「羲和 · security-reviewer · 等待可用执行槽位」，状态「排队中」，阶段进度只有「排队准备」；主对话里也有「羲和|排队中」状态条。

### 结论：子智能体**有用**，是状态映射错了

用真实数据验证（`~/.codexh/codexh.sqlite` + `~/.codexh/logs/runtime.jsonl`）：

- 该线程 `6dcbd30a-a943-42f3-b6be-36a4b07a6ebd`（`/root/security-reviewer`）：`turn_runs.status = completed`，189,663 prompt / 4,205 completion tokens，跑了 65 秒，最终 assistant 消息落库（RiskEmpRequestValidator / OpenService 的 SQL 注入面结论）。
- 主线程 `wait_agent` 拿到的返回是 `{"agents":[{"status":"queued","summary":"### C. status / emp_state / ..."}]}` —— **summary 内容是完整的真实产出，只有 `status` 字段被写成了 queued**。也就是说结果交付没问题，是状态标注误导主模型（会让它以为子任务还在排队）。
- 但 `threads.status = idle`（`updated_at` 比 turn 完成时间晚 12ms）。

### 根因链（三处叠加）

1. `packages/agent-runtime/src/index.ts` 约 5658 行，成功收尾时：`status = terminalDisposition === "awaiting_user_confirmation" || providerOutputLimitEncountered ? "idle" : "completed"`。`providerOutputLimitEncountered` 是**整轮粘性标记**（约 3542 行置 true，恢复重试后不复位）。runtime.jsonl 里有 `02:49:39 provider.output_limit attempt=1 "response reached its output limit"`，之后重试成功、turn 正常 completed，但线程被写成 `idle`。子智能体不可能命中 `awaiting_user_confirmation`（`resolveTerminalTurnDisposition` 对 child 强制 `gpaStage: "off"`，且该线程 gpa_state_json 只有 `{"fullAccess":true}`）。
2. `apps/desktop/src/main/app.ts` 约 4557 行 `buildSubagentEnvelope`：`thread.status === "idle" → "queued"`。这个映射只在「创建了但从未派发」时才成立（`spawnAgent` 里 `status: queued ? "idle" : "running"`），却被当成了 idle 的通用语义。
3. `apps/desktop/src/renderer/cards/runtime-cards.tsx` 约 288 行 `resolveSubagentDisplayState`：`if (queued || result?.status === "queued") return "queued"` 排在 completed/failed/interrupted **之前**，于是排队把终态全遮掉；`getSubagentPhases` 更是在 queued 时直接短路返回「排队准备」。

## 修：记忆改造导致 codexh 启动崩溃（已完成，真实环境已验证启动）

现象：弹窗「codexh 启动失败 — `no such column: fingerprint`」，栈顶 `DatabaseService.bootstrap`（`dist/main/index.js`）。

### 根因（一个会复发的排序错误）

`fingerprint` 唯一索引被写进了 `bootstrap()` 的**建表 `exec` 大字符串**里，而它跑在 `ensureColumns()` **之前**。老库里 `self_improvement_memories` 已存在 → `CREATE TABLE IF NOT EXISTS` 是空操作 → 列还没 `ALTER TABLE` 补上 → 建索引直接抛错，`ensureColumns()` 根本没机会执行。

**铁律**：引用 `ensureColumn` 新增列的索引/视图，只能写在 `ensureColumns()` 里、且在该 `ensureColumn` 之后；建表 exec 块里只允许出现初始 schema 就有的列。

### 改动

- `storage.ts`：删掉 exec 块里那个索引（`ensureColumns` 里那份保留），该处留注释说明顺序约束；新增 `backfillMemoryFingerprints()`——老行 `fingerprint=''` 永远匹配不到，会被下次提炼当新事实重复写入，所以按 `(scope, project_id, title)` 推导指纹回填，**JS 侧先去重**，同身份的第二条留空（部分唯一索引 `WHERE fingerprint <> ''` 忽略它，保证索引能建、回填不会中止启动）。
- `tests/memory-schema-migration.test.ts`（新）：用**老表结构**（无 fingerprint/source/content_hash）建库 → `new DatabaseService()` 不抛错；断言老行全部可读、global 行的 project_id 归一为 NULL、重复身份留空、重开库幂等、新库 `mergeSelfImprovementMemory` 仍是 created→updated。

### 真实数据验证（方法可复用）

主库 1.9 GB（`~/.codexh/codexh.sqlite`），**不复制**：
